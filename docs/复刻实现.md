# 复刻实现

> 复刻 **ozonbox** 浏览器插件项目

## 1. 本阶段范围

本阶段只复刻登录认证及维持认证状态所必需的客户端行为，不扩展商品采集、上架、店铺管理等业务能力。

- 唯一事实来源：仓库根目录 `ozonbox/` 中的原项目源码。
- 目标：将原项目客户端对 `erp.ozonbox.top` 的认证依赖迁移到本仓库已有的 FastAPI 认证服务。
- 实施顺序：先记录原项目交互和功能，再定义迁移映射，最后修改实现并验收。
- 取证规则：只记录源码中能够确认的行为；未观察到的接口明确标注，不推测原服务端实现。
- 数据边界：当前证据不要求修改 `User` 数据模型，因此本阶段不新增用户名、手机号字段，也不产生数据库迁移。

## 2. 原项目认证入口与 API 地址

原项目是 Manifest V3 Chrome 扩展，认证链路分布如下：

| 入口 | 文件 | 认证职责 |
| --- | --- | --- |
| Popup | `ozonbox/popup/popup.html`、`ozonbox/popup/popup.js` | 输入用户名/手机号和密码、登录、恢复本地会话、加载店铺、本地登出 |
| Background service worker | `ozonbox/background/service-worker.js` | 从 ERP 页面 `localStorage` 同步 token/username；接收凭据保存消息 |
| Content script | `ozonbox/content/collector.js` | 消费登录状态、执行 Bearer 请求、遇到 401 清理扩展登录状态 |
| 扩展配置 | `ozonbox/manifest.json` | 声明 popup、service worker、content script、storage/scripting 权限及 host permissions |

`popup/popup.js` 的 `getApiBase()` 明确给出两个基础地址：

| 条件 | API 基础地址 |
| --- | --- |
| popup 页面 hostname 为 `localhost` 或 `127.0.0.1` | `http://localhost:8080/api` |
| 其他情况 | `https://erp.ozonbox.top/api` |

以下接口表均以 `${API_BASE}` 表示上述基础地址。

## 3. 原项目网络交互清单

### 3.1 认证接口

源码中只观察到一个直接认证接口。

#### `POST ${API_BASE}/auth/login`

| 项目 | 已确认行为 |
| --- | --- |
| 触发位置 | Popup 点击登录按钮后执行 `handleLogin()` |
| 请求头 | `Content-Type: application/json` |
| 请求体 | `{ "username": string, "password": string }` |
| 用户名语义 | Popup 输入框 placeholder 为“用户名/手机号” |
| 成功条件 | `data.code === 200 && data.data?.token` |
| 使用的成功字段 | 必需 `data.data.token`；可选 `data.data.username` |
| 显示名规则 | `data.data.username || 输入的 username || '已登录'` |
| 登录失败信息 | `data.message`；没有该字段时显示“用户名或密码错误” |
| 成功后的本地状态 | 将 token、username 写入 `chrome.storage.local`，再回读 token 验证保存结果 |
| 成功后的动作 | 显示已登录 UI、加载店铺、向 active tab 发送登录状态变化消息 |

该请求没有使用统一 Bearer 请求封装，因为登录前尚无 token。源码只消费上述响应字段，不能据此推导原服务端的其他响应内容。

### 3.2 登录后的认证依赖接口

这些接口不是“登录接口”，但其调用依赖已经建立的认证状态。

#### `GET ${API_BASE}/store/list`

| 项目 | 已确认行为 |
| --- | --- |
| 触发时机 | Popup 启动恢复到 token 后；登录成功后；content script 需要加载店铺时 |
| 认证头 | `Authorization: Bearer <token>` |
| 功能 | 获取登录用户可用店铺，供后续选择店铺和业务请求使用 |
| 401 行为 | 清除登录状态；popup 切回登录 UI，content script 清除其内存及 storage 中的认证相关状态 |

#### `POST ${API_BASE}/ozon/products/info?clientId=<clientId>`

| 项目 | 已确认行为 |
| --- | --- |
| 触发位置 | Content script 的 `queryCategoryByProductId(clientId, productId)` |
| 认证头 | `Authorization: Bearer <token>` |
| 请求体 | `{ "product_id": parseInt(productId) }` |
| 功能 | 查询商品的 `description_category_id` 与 `type_id` |
| 401 行为 | 调用统一的 `handleUnauthorizedResponse()` 清理登录状态并停止本次处理 |

#### `POST ${API_BASE}/online-product/info?storeId=<selectedStoreId>`

| 项目 | 已确认行为 |
| --- | --- |
| 触发时机 | 上一个类目查询没有得到结果，且存在 `selectedStoreId` 时作为后续查询 |
| 认证头 | `Authorization: Bearer <token>` |
| 请求体 | `{ "product_id": [parseInt(productId)] }` |
| 使用的响应字段 | `data.code === 200` 时读取 `data.data.result` 或 `data.data.items[0]` 中的类目和类型字段 |
| 401 行为 | 调用统一的 `handleUnauthorizedResponse()` 清理登录状态并停止本次处理 |

#### `POST ${API_BASE}/product-record/save`

| 项目 | 已确认行为 |
| --- | --- |
| 触发位置 | Content script 的保存和编辑流程 |
| 前置条件 | 必须有 token，并先完成采集商品类目确认 |
| 认证头 | `Authorization: Bearer <token>` |
| 请求体 | `buildProductRecordPayload(collectedProduct)` 生成的 JSON |
| 功能 | 保存采集商品记录；编辑流程成功后可打开 ERP 商品历史编辑页面 |
| 401 行为 | 调用统一的 `handleUnauthorizedResponse()` 清理登录状态并停止本次处理 |

上述三个商品接口属于“认证后的业务调用”，本阶段只保留它们与认证状态、Bearer header 和 401 生命周期的关系，不在本阶段复刻其业务协议。

### 3.3 统一 Bearer 请求行为

`ozonbox/popup/popup.js` 的 `apiRequest()` 负责 popup 的认证后请求：

1. 从 `chrome.storage.local` 读取 token。
2. 请求 `${API_BASE}${path}`，存在 token 时设置 `Authorization: Bearer <token>`。
3. HTTP 401 时执行 `clearLoginState('登录已过期，请重新登录')` 并抛出错误。
4. 其他非 401 响应由具体调用方继续解析。

`ozonbox/content/collector.js` 没有调用 popup 内的函数，而是通过共享的 `handleUnauthorizedResponse(response)` 统一处理其各处请求的 401。两个运行上下文不能直接复用同一函数，但它们遵循相同的状态清理规则。

### 3.4 源码中未观察到的认证网络接口

在已调查的 popup、background 和 content script 源码中未观察到：

- 注册接口；
- 后端登出接口；
- 刷新 token 接口；
- 独立 token 校验接口。

因此原项目的登出是本地状态删除，启动恢复依据也是本地是否存在 token；不能将“未观察到”写成原服务端一定不具备这些能力。

## 4. 非网络认证交互与状态生命周期

### 4.1 Chrome storage

| Key | 写入方 | 读取/消费方 | 清理时机 |
| --- | --- | --- | --- |
| `token` | Popup 登录、background ERP 页面同步、`SAVE_CREDENTIALS` handler | Popup、content script | Popup 登出或 401；content script 401 |
| `username` | Popup 登录、background ERP 页面同步、`SAVE_CREDENTIALS` handler | Popup及登录状态消息 | Popup 登出或 401；content script 401 |
| `stores` | 店铺加载流程 | Popup、content script | Content script 认证失效时；其他清理由对应流程负责 |
| `selectedStoreId` | 店铺选择流程 | Popup、content script 和认证后业务请求 | Content script 认证失效时；其他清理由对应流程负责 |

Popup 启动执行 `checkLoginStatus()`：存在 token 就构造当前用户、显示已登录 UI 并调用 `loadStores()`；不存在 token 就显示登录 UI。username 不存在时仅将显示名设为“已登录”，不会代替 token 完成认证。

### 4.2 Popup 与 content script 消息

Popup 在登录成功、登出等登录状态变化后向 active tab 发送：

```js
{
  type: 'ERP_LOGIN_STATE_CHANGED',
  token,
  username,
  stores,
  selectedStoreId
}
```

Content script 接收该消息后更新其内存中的认证及店铺状态。它还监听 `chrome.storage.onChanged` 中的 token 变化，以同步不同扩展上下文之间的状态。

### 4.3 ERP 页面凭据同步旁路

Background 监听 tab URL 更新。当变更后的 URL 包含 `erp.ozonbox.top` 时，通过 `chrome.scripting.executeScript` 在页面上下文执行 `checkERPLogin()`：

1. 从 ERP 页面 `localStorage` 读取 `token` 和 `username`。
2. 两者都存在时返回 `{ token, username }`，否则返回 `null`。
3. Background 将非空结果写入扩展的 `chrome.storage.local`。

Background 还处理 `SAVE_CREDENTIALS` 消息，将消息中的 token、username 写入 `chrome.storage.local`。这些是扩展内部/页面间状态同步，不是后端网络接口。

该旁路依赖原 ERP 域名及其页面 storage 契约。迁移到自有服务时，不把它无依据移植到当前 WXT 扩展；当前扩展应以自己的登录 UI 和 `plugin_auth` 会话为准。

## 5. 自有服务认证契约

当前 FastAPI 服务已经提供 canonical 认证接口：

| 接口 | 请求 | 成功响应 | 认证要求 |
| --- | --- | --- | --- |
| `POST /api/auth/register` | `{ email, password, name? }` | `{ access_token, token_type, user }`，HTTP 201 | 无 |
| `POST /api/auth/login` | `{ email, password }` | `{ access_token, token_type: 'bearer', user }` | 无 |
| `GET /api/auth/me` | 无 | 当前用户对象 | `Authorization: Bearer <access_token>` |

实现证据：

- 路由：`backend/app/api/routers/auth.py`
- 请求/响应模型：`backend/app/schemas/auth.py`
- JWT 与密码哈希：`backend/app/core/security.py`
- Bearer token 解析和当前用户依赖：`backend/app/api/dependencies.py`
- 用户模型：`backend/app/models/user.py`
- 现有认证测试：`backend/tests/test_auth.py`

部署时必须通过环境变量设置真实的 `JWT_SECRET_KEY`；`backend/app/core/config.py` 中的默认值只适合开发环境。

## 6. 迁移映射与兼容边界

### 6.1 契约映射

| 原 Ozonbox | 自有实现 | 迁移方式 |
| --- | --- | --- |
| `username`（UI 语义为用户名/手机号） | `email` | 客户端登录 UI 和请求使用既有 email 契约 |
| `{ username, password }` | `{ email, password }` | 不在后端增加推测性的 username/phone alias |
| `data.data.token` | `access_token` | 客户端按自有 `AuthResponse` 读取 |
| `data.data.username` | `user`（含 email/name 等既有字段） | UI 从会话中的 user 展示身份 |
| `chrome.storage.local.token/username` | WXT 的 `plugin_auth: AuthSession` | 保留当前单一会话对象，不复制旧的分散 key |
| 是否存在 token 即视为已登录 | 启动时用 `GET /api/auth/me` 验证已保存 token | 过期/无效 token 由统一 401 处理清理 |
| `https://erp.ozonbox.top/api` | 当前设置中的自有 API base + `/api` | 复用 WXT 的可配置 `apiBaseUrl` |
| HTTP 401 清理旧 storage 状态 | HTTP 401 清理 `plugin_auth` | 复用 `extension/lib/utils/api.ts` 的集中 request wrapper |
| 本地登出 | 删除 `plugin_auth` | 不新增没有事实依据的 logout API |

### 6.2 当前代码可复用能力

当前 WXT 扩展已经具备：

- `extension/lib/utils/api.ts`：集中处理 base URL、Bearer header、错误详情和 401 会话清理；提供 `login()`、`register()`、`getCurrentUser()`。
- `extension/lib/utils/storage.ts`：集中读写/删除 `plugin_auth`。
- `extension/entrypoints/popup/App.vue`：自有 email/password 登录注册 UI 和本地登出。

因此迁移实现不得新增第二套 request/storage wrapper。需要补齐的最小生命周期行为是：popup 启动发现本地会话后调用现有 `getCurrentUser()` 验证 token；验证失败后同步清空页面内的 session 引用。

当前 Web 前端也使用自有 `/api/auth/*` 契约。其通用请求和下载请求应共享认证 header 与 401 清理规则，避免两套近似逻辑产生不一致；改动不得破坏已有请求超时处理。

### 6.3 明确不实施的内容

- 不修改后端 `User` 模型，不新增 username/phone 字段，不创建无必要的数据迁移。
- 不增加兼容原响应 `{ code, data: { token } }` 的后端接口。
- 不把原 ERP 页面 `localStorage` 注入和 `SAVE_CREDENTIALS` 旁路迁移到当前 WXT 扩展。
- 不在本阶段复刻店铺、商品类目、商品保存接口的业务实现。
- 不重构与认证生命周期无关的采集或管理功能。

## 7. 预期认证流程

### 7.1 首次登录/注册

1. 用户在扩展中输入 email/password（注册可附带 name）。
2. 客户端请求自有 `/api/auth/login` 或 `/api/auth/register`。
3. 成功后将完整 `AuthSession` 保存到 `plugin_auth`。
4. 后续请求由统一 wrapper 添加 `Authorization: Bearer <access_token>`。

### 7.2 扩展重启恢复

1. 从 `plugin_auth` 读取会话。
2. 没有会话时显示登录 UI。
3. 有会话时请求 `/api/auth/me` 验证 token。
4. 验证成功后使用服务端返回的当前用户刷新本地 session 用户信息。
5. 返回 401 时由统一 wrapper 删除 `plugin_auth`，popup 同步切回未登录状态。

### 7.3 登出和认证失效

- 主动登出：只删除本地 `plugin_auth` 并刷新 UI。
- 被动失效：任意认证请求收到 HTTP 401 时，由统一 request wrapper 删除 `plugin_auth` 并抛出明确错误；调用页面同步释放其内存 session。

## 9. 验收标准

- 文档将认证接口、认证后业务接口和非网络状态同步明确分开。
- 所有原项目行为均能定位到 `ozonbox/` 源码，未观察到的能力没有被推测实现。
- 自有后端继续使用现有 `/api/auth/register`、`/api/auth/login`、`/api/auth/me` canonical 契约，现有认证测试通过。
- 扩展登录/注册保存 `plugin_auth`，重启时验证 token，401 时清理会话并显示未登录状态。
- Bearer header、错误解析、401 清理和 storage 操作继续通过现有公共函数复用。
- Web 前端的普通请求与下载请求采用一致的认证失效规则，已有超时能力保持不变。
- 前端与扩展通过各自的 TypeScript 检查/构建；最终差异不包含认证迁移之外的功能。
